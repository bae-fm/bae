默认情况下，bae 会在音乐文件和资料库元数据离开你的机器前加密它们，存储提供商只能看到密文。cloud home 也可以设置为以结构化、可浏览路径明文保存所有内容；见下面的[存储模式](#存储模式opaque-和-browsable)。

## 存储模式：opaque 和 browsable

配置 cloud home 时，你会选择它如何保存对象。这个选择对所有提供商都可用，并且对该 home 固定。

- **Opaque**（默认）— 每个对象都用资料库密钥加密，并保存到混淆的、按内容寻址的路径，例如音频的 `storage/ab/cd/{id}`、封面的 `images/ab/cd/{id}`。提供商只能看到不可读路径上的密文。选择它可避免提供商或任何拿到 bucket 访问权的人读取资料库内容。
- **Browsable** — 对象不加密保存，保留真实文件名，并按专辑和发行版本 ID 使用稳定路径：发行版本文件位于 `storage/{album_id}/{release_id}/{import_folder}/01 Track Title.flac`（镜像导入时的文件夹），封面位于 `images/{album_id}/{release_id}/cover.jpg`，艺人图片位于 `images/{artist_id}/artist.jpg`。你可以在提供商网页界面或文件浏览器中看到真实文件名，并直接播放或复制文件。内容不加密，因此保护完全依赖提供商自身的访问控制。

browsable 表示“不混淆”，不是“用人类可读名称组织”：目录名是 ID，而不是艺人或专辑文本。使用 ID 可以从结构上避免冲突；每个发行版本写入自己的 `{release_id}` 文件夹，不会与另一个发行版本合并或覆盖。它也不表示公开访问：bucket 仍由提供商凭据控制，和 opaque home 一样；该模式只改变已经有访问权的人看到的是明文还是密文。

本页其余部分描述 **opaque** home。browsable home 不执行下面的加密步骤，而是把每个对象作为明文写入基于 ID 的路径。

## 资料库密钥

每个资料库都有一个 256 位主加密密钥，在创建资料库时生成，并保存在操作系统钥匙串中（macOS Keychain、Windows Credential Manager 或 Linux Secret Service）。密钥不会以明文写入磁盘。

## 文件加密

文件使用 XChaCha20-Poly1305，按 64 KB 分块加密。每个文件都有一个随机 nonce，并把它放在加密数据前面。这意味着：

- 相同文件会产生不同密文（因为随机 nonce）
- 文件可以独立解密（文件之间没有依赖）
- 分块加密支持流式播放所需的高效范围请求

## Cloud home 加密

在 opaque home 中，cloud home 的所有内容都会加密：

- **变更集** — 使用资料库密钥加密
- **快照** — 使用资料库密钥加密
- **图片** — 使用资料库密钥加密
- **Membership 条目** — 使用资料库密钥加密
- **封装密钥** — 通过 sealed box 加密给每台设备（见 [Membership](/zh-hans/architecture/membership)）

head 文件（每台设备的序号）也会加密。存储提供商只能看到不透明数据块和键路径。

## 密钥管理

资料库密钥保存在操作系统钥匙串中，并按资料库命名隔离。如果你在多台设备上使用 bae，密钥会通过 membership 系统分发：它被 sealed box 加密给你的个人公钥，因此只有你的设备可以打开。

如果你失去所有设备的访问权，并且没有钥匙串备份，bucket 中的资料库数据将无法恢复。这是设计的一部分：没有服务器端恢复机制。
