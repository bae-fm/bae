O cloud home é um único local remoto de armazenamento para uma biblioteca: uma pasta do Google Drive, um bucket S3, uma pasta do Dropbox. Ele contém arquivos de edições, changesets de metadados, arte, snapshots e a cadeia de membros. Em um home **opaco** (padrão), toda confiança fica na criptografia, não no backend de armazenamento: o provedor armazena texto cifrado em chaves ofuscadas. Um home também pode ser configurado como **navegável**, armazenando tudo sem criptografia em caminhos estáveis baseados em ids com nomes reais de arquivos; veja [Modos de armazenamento](/pt-br/architecture/encryption#modos-de-armazenamento-opaco-e-navegavel).

## O trait CloudHome

O trait `CloudHome` é a abstração que torna bae independente de backend. Tudo acima do trait é universal. Tudo abaixo dele se adapta ao provedor cloud específico.

### O que é universal (acima do trait)

- **Layout do cloud home** — `changes/`, `heads/`, `snapshot.db`, `images/`, `storage/`, `membership/`, `keys/`. Mesmos caminhos lógicos independentemente do backend. Um home opaco divide áudio e arte em `storage/` e `images/` por hash do id; um home navegável os coloca sob os mesmos dois prefixos em caminhos estáveis baseados em ids com nomes reais (`storage/{album_id}/{release_id}/{import_folder}/01 Track.flac`, `images/{album_id}/{release_id}/cover.jpg`).
- **Criptografia** — uma chave simétrica por biblioteca; em um home opaco, tudo é criptografado antes de sair do dispositivo. Um home navegável pula a criptografia e armazena texto em claro; o sufixo `.enc` é removido.
- **Protocolo de sincronização** — changesets, snapshots e resolução de conflitos por last-writer-wins. Mesmo algoritmo em todos os lugares.
- **Cadeia de membros** — log somente anexável com assinaturas Ed25519 e chave de criptografia envelopada para a chave pública de cada membro.

### O que varia (abaixo do trait)

- **API de armazenamento** — como arquivos são lidos e gravados: API S3, API Google Drive, sistema de arquivos local, etc.
- **Gerenciamento de acesso** — como um dispositivo novo obtém acesso ao armazenamento: acesso a pasta ou emissão de credenciais.
- **Autenticação** — como um dispositivo novo se autentica: sua conta cloud ou credenciais embutidas.
- **Notificações de mudança** — clouds de consumo aceitam notificações push; S3 exige polling.

### Interface do trait

```rust
trait CloudHome {
    // Storage -- same interface, different API underneath
    fn write(path, data) -> Result;
    fn read(path) -> Result<Bytes>;
    fn read_range(path, start, end) -> Result<Bytes>;
    fn list(prefix) -> Result<Vec<String>>;
    fn delete(path) -> Result;
    fn exists(path) -> Result<bool>;

    // Access management -- varies by backend
    fn grant_access(member_email_or_id) -> Result<JoinInfo>;
    fn revoke_access(member_email_or_id) -> Result;
}

Os chamadores, como o mecanismo de sincronização, o envio de imagens e o armazenamento de arquivos, usam essa interface diretamente. Eles não precisam saber qual backend está por trás.
```

## Gerenciamento de acesso

Como `grant_access` e `revoke_access` funcionam depende do backend. Clouds de consumo (Google Drive, Dropbox, OneDrive) compartilham a pasta pela API do provedor: você entra na conta no novo dispositivo e a pasta já está acessível. Backends compatíveis com S3 emitem credenciais IAM com escopo para cada dispositivo, embutidas no código de convite.

Nos dois casos, a chave de criptografia é entregue separadamente pela cadeia de membros, envelopada para a chave pública do novo dispositivo.
