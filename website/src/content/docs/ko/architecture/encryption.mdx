기본적으로 bae는 음악 파일과 라이브러리 메타데이터가 컴퓨터를 떠나기 전에 암호화하며, 저장소 제공자는 암호문만 봅니다. 클라우드 홈은 대신 구조화되고 탐색 가능한 경로에 모든 것을 평문으로 저장하도록 설정할 수도 있습니다. 아래 [저장소 모드](#storage-modes-opaque-and-browsable)를 참고하세요.

## 저장소 모드: 불투명과 탐색 가능

클라우드 홈을 설정할 때 객체 저장 방식을 선택합니다. 이 선택은 해당 홈에 고정되며 모든 제공자에서 제공됩니다.

- **불투명**: 기본값. 모든 객체를 라이브러리 키로 암호화하고 난독화된 콘텐츠 주소 경로에 저장합니다. 오디오는 `storage/ab/cd/{id}`, 아트워크는 `images/ab/cd/{id}`입니다. 제공자는 알아볼 수 없는 키 아래 암호문만 봅니다. 제공자 또는 버킷에 접근한 누군가가 라이브러리를 읽지 못하게 하려면 이 모드를 선택하세요.
- **탐색 가능**: 객체를 암호화하지 않고 파일의 실제 이름을 유지해, 앨범과 릴리스 ID로 된 안정적인 경로 아래 저장합니다. 릴리스 파일은 가져온 폴더를 반영한 `storage/{album_id}/{release_id}/{import_folder}/01 Track Title.flac`, 아트워크는 `images/{album_id}/{release_id}/cover.jpg`와 `images/{artist_id}/artist.jpg`입니다. 제공자의 웹 UI나 파일 브라우저로 버킷을 열어 실제 파일명을 보고 직접 재생하거나 복사할 수 있습니다. 아무것도 암호화되지 않으므로 홈의 보호는 전적으로 제공자의 접근 제어에 달려 있습니다.

탐색 가능은 *가려지지 않음*을 뜻하지 *사람이 읽는 이름으로 폴더를 만듦*을 뜻하지 않습니다. 폴더는 아티스트/앨범 텍스트가 아니라 ID입니다. ID를 쓰면 이름 변환 없이도 충돌을 피할 수 있습니다. 각 릴리스는 자기 `{release_id}` 폴더에 한 번 기록되며 다른 릴리스 파일과 충돌하거나 합쳐지지 않습니다. 같은 앨범의 두 릴리스는 앨범 아래 형제 폴더가 됩니다. 또한 공개라는 뜻도 아닙니다. 버킷 접근은 불투명 홈과 똑같이 제공자의 자격 증명으로 막혀 있습니다. 모드는 이미 접근 권한이 있는 사람이 저장 내용을 읽을 수 있는지만 바꿉니다.

나머지 문서는 **불투명** 홈을 설명합니다. 탐색 가능 홈은 아래 암호화를 수행하지 않으며 각 객체를 ID 구조의 키에 평문으로 씁니다.

## 라이브러리 키

각 라이브러리는 256비트 마스터 암호화 키를 가집니다. 라이브러리를 만들 때 생성되며 OS 키링: macOS Keychain, Windows Credential Manager, Linux Secret Service에 저장됩니다. 키는 평문으로 디스크에 기록되지 않습니다.

## 파일 암호화

파일은 XChaCha20-Poly1305로 64KB 청크 단위 암호화됩니다. 각 파일은 암호화된 blob 앞에 임의 nonce를 붙입니다. 이 방식의 의미는 다음과 같습니다.

- 같은 파일도 서로 다른 암호문을 만듭니다: 임의 nonce
- 파일은 독립적으로 복호화할 수 있습니다: 파일 간 의존 없음
- 청크 기반 암호화는 스트리밍을 위한 효율적인 범위 요청을 지원합니다

## 클라우드 홈 암호화

불투명 홈에서는 클라우드 홈의 모든 것이 암호화됩니다.

- **변경 세트** — 라이브러리 키로 암호화
- **스냅샷** — 라이브러리 키로 암호화
- **이미지** — 라이브러리 키로 암호화
- **멤버십 항목** — 라이브러리 키로 암호화
- **래핑된 키** — 각 기기에 sealed box로 암호화: [멤버십](/ko/architecture/membership) 참고

헤드 파일: 기기별 시퀀스 번호도 암호화됩니다. 저장소 제공자는 불투명한 blob과 키 경로만 봅니다.

## 키 관리

라이브러리 키는 OS 키링에 라이브러리별 네임스페이스로 저장됩니다. 여러 기기에서 bae를 사용하면 키는 멤버십 시스템을 통해 배포됩니다. 개인 공개 키로 sealed box 암호화되므로 내 기기만 풀 수 있습니다.

모든 기기에 대한 접근을 잃고 키링 백업도 없다면 버킷의 라이브러리 데이터는 복구할 수 없습니다. 이는 의도된 설계입니다. 서버 측 복구 메커니즘은 없습니다.
