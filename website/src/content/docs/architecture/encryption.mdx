title: Encryption
description: How bae encrypts your data

By default, bae encrypts your music files and library metadata before they leave your machine, and the storage provider sees ciphertext only. A cloud home can instead be set to store everything in the clear at structured, navigable paths — see [Storage modes](#storage-modes-opaque-and-browsable) below.

## Storage modes: opaque and browsable

When you set up a cloud home you choose how it stores its objects. The choice is fixed for that home and is offered for every provider.

- **Opaque** (the default) — every object is encrypted with the library key and stored at an obfuscated, content-addressed path (`storage/ab/cd/{id}` for audio, `images/ab/cd/{id}` for artwork). The provider sees only ciphertext at unintelligible keys. Choose this when you don't want the provider — or anyone who reaches the bucket — to read your library.
- **Browsable** — objects are stored unencrypted, with the file's real name intact, under a stable path keyed by the album and release ids: `storage/{album_id}/{release_id}/{import_folder}/01 Track Title.flac` for release files (mirroring the folder the release was imported from), `images/{album_id}/{release_id}/cover.jpg` and `images/{artist_id}/artist.jpg` for artwork. You can open the bucket in the provider's web UI or a file browser, see your actual filenames, and play or copy them directly. Nothing is encrypted, so the home's protection rests entirely on the provider's own access control.

Browsable means *not obscured*, not *human-named*: the folders are ids rather than artist/album text. Using ids keeps the layout collision-free by construction — each release is written into its own `{release_id}` folder once and never collides with or absorbs another release's files — without any name-mangling. (Two releases of the same album are sibling folders under the album.) It does not mean public, either: access to the bucket is gated by the provider's credentials exactly as it is for an opaque home; the mode only changes whether what's stored is legible to whoever already has access.

The rest of this page describes an **opaque** home. A browsable home performs none of the encryption below — each object is written as plaintext at its id-structured key.

## Library key

Each library has a 256-bit master encryption key, generated when the library is created and stored in your OS keyring (macOS Keychain, Windows Credential Manager, or Linux Secret Service). The key never touches disk in plaintext.

## File encryption

Files are encrypted with XChaCha20-Poly1305 in 64 KB chunks. Each file gets a random nonce prepended to the encrypted blob. This means:

- Identical files produce different ciphertext (random nonce)
- Files can be decrypted independently (no dependency between files)
- Chunk-based encryption supports efficient range requests for streaming

## Cloud home encryption

On an opaque home, everything in the cloud home is encrypted:

- **Changesets** — encrypted with the library key
- **Snapshots** — encrypted with the library key
- **Images** — encrypted with the library key
- **Membership entries** — encrypted with the library key
- **Wrapped keys** — encrypted to each device via sealed boxes (see [Membership](/architecture/membership))

Head files (per-device sequence numbers) are also encrypted. The storage provider sees only opaque blobs and key paths.

## Key management

Your library key is stored in the OS keyring under a library-specific namespace. If you use bae on multiple devices, the key is distributed via the membership system — encrypted to your personal public key using a sealed box, so only your devices can unwrap it.

If you lose access to all devices and don't have a backup of your keyring, the library data in the bucket is unrecoverable. This is by design — there is no server-side recovery mechanism.
