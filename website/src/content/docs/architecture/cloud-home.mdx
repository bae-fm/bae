The cloud home is a single remote storage location for a library -- one Google Drive folder, one S3 bucket, one Dropbox folder. It holds release files, metadata changesets, artwork, snapshots, and the membership chain. On an **opaque** home (the default) all trust lives in cryptography, not the storage backend -- the provider stores ciphertext at obfuscated keys. A home can instead be set to **browsable**, storing everything unencrypted at stable, id-keyed paths with real filenames; see [Storage modes](/architecture/encryption#storage-modes-opaque-and-browsable).

## The CloudHome trait

The `CloudHome` trait is the abstraction that makes bae backend-agnostic. Everything above the trait is universal. Everything below it adapts to the specific cloud provider.

### What's universal (above the trait)

- **Cloud home layout** -- `changes/`, `heads/`, `snapshot.db`, `images/`, `storage/`, `membership/`, `keys/`. Same logical paths regardless of backend. An opaque home shards audio and artwork under `storage/` and `images/` by a hash of their id; a browsable home lays them out under the same two prefixes at stable id-keyed paths with real filenames (`storage/{album_id}/{release_id}/01 Track.flac`, `images/{album_id}/{release_id}/cover.jpg`).
- **Encryption** -- one symmetric key per library; on an opaque home everything is encrypted before it leaves the device. A browsable home skips encryption and stores plaintext (the `.enc` suffix is dropped).
- **Sync protocol** -- changesets, snapshots, conflict resolution via last-writer-wins. Same algorithm everywhere.
- **Membership chain** -- append-only log with Ed25519 signatures, encryption key wrapped to each member's public key.

### What varies (below the trait)

- **Storage API** -- how files are actually read and written (S3 API vs Google Drive API vs local filesystem, etc.).
- **Access management** -- how a new device gets storage access (folder access vs credential minting).
- **Authentication** -- how a new device authenticates (your cloud account vs embedded credentials).
- **Change notifications** -- consumer clouds support push notifications; S3 requires polling.

### The trait interface

```rust
trait CloudHome {
    // Storage -- same interface, different API underneath
    fn write(path, data) -> Result;
    fn read(path) -> Result<Bytes>;
    fn read_range(path, start, end) -> Result<Bytes>;
    fn list(prefix) -> Result<Vec<String>>;
    fn delete(path) -> Result;
    fn exists(path) -> Result<bool>;

    // Access management -- varies by backend
    fn grant_access(member_email_or_id) -> Result<JoinInfo>;
    fn revoke_access(member_email_or_id) -> Result;
}

Callers (sync engine, image uploader, file storage) use this interface directly. They do not know or care which backend they are talking to.
```

## Access management

How `grant_access` and `revoke_access` work depends on the backend. Consumer clouds (Google Drive, Dropbox, OneDrive) share the folder via the provider's API -- you sign into your account on the new device and the folder is already accessible. S3-compatible backends mint scoped IAM credentials for each device, embedded in the invite code.

In both cases, the encryption key is delivered separately via the membership chain, wrapped to the new device's public key.
